# 压测记录

## 怎么压

```bash
cd server
uv run python -m app.cli seed-load --classes 12 --per-class 50   # 压测学校：12 个班、600 名学生、每班一份 10 道客观题的作业
uv run uvicorn app.main:app --port 8000 --workers 2 --no-access-log
uv run python -m app.devtools.loadtest --users 100 --duration 120 --think 5
uv run python -m app.cli seed-load --reset                        # 再压一遍前清掉作答
```

- 每个虚拟学生：登录 → 首页（账号、站内信、作业列表）→ 打开作业 → 逐题作答（自动保存）→ 提交 → 错题本、今日背诵，之后反复刷新。每步之间停顿 `--think` 秒（随机 0.5～1.5 倍）。虚拟老师反复看作业列表、作业报告、批改队列。
- 一个压测进程模拟 100 人左右就到上限（客户端自己跑不动）。人多时开几个进程，用 `--offset` 错开学生账号。
- 压测学校的 AI 月额度是 0，不会调用大模型。

## 结果（2026-11-03，本机）

环境：i5-13400（16 线程）、32 GB 内存；数据库是本地开发用的 PostgreSQL，压测客户端也在同一台机器上。服务器上的数字会更低，进学校前要在试点服务器上再压一次。

| 场景 | API 进程 | 请求数 | 失败 | 各接口 p50 | 各接口 p95 | 提交作业 p50 / p95 |
|---|---|---|---|---|---|---|
| 600 名学生同时做作业，每步停顿约 5 秒，2 分钟 | 2 | 22,296（约 160 个/秒） | 0 | 16–34 ms | 52–95 ms | 70–90 / 220–270 ms |
| 600 名学生，每步停顿约 1 秒（远比真人频繁） | 2 | 25,357（约 260 个/秒） | 4 | 1.5–2 s | 2–2.5 s | — |
| 100 名学生，每步停顿约 1 秒 | 1 | 10,289（约 160 个/秒） | 0 | 16–28 ms | 40–70 ms | 85 / 243 ms |

- 单个 API 进程每秒能处理约 170 个请求，到这里 CPU 就满了（Python 一个进程只用一个核），再多请求就排队。
- 学生做一道题通常要几十秒，600 人同时在线时实际请求远少于每秒 160 个。试点用 2 个进程（2 核 4 G）够用；人更多时加进程（`API_WORKERS`）或加机器。
- 问一问、AI 批改的速度取决于模型平台，不在这次压测范围：批改每个 Worker 同时最多 3 份，问一问每条回复几秒。

## 压测发现并修好的问题

1. **300 人同时在线时服务卡死**（所有请求超时）。同步接口分几段在线程池里执行（校验登录 → 接口 → 响应校验），每段之间都要重新排队等线程，排队时请求占着数据库连接。人一多，排队的请求把连接池占满，正在执行的线程拿不到连接，互相卡死到超时。修复：校验完登录、接口执行完都马上结束事务、归还连接（`core/routing.py`），线程数设得比连接池上限小（`API_THREADS`，启动时检查）。
2. **全班同时登录可能把内存用光**。密码哈希（Argon2）默认每次校验要 64 MB 内存，几十个并发登录就要 2 GB，试点服务器只有 2.4 GB。改成 OWASP 建议的参数（19 MB），每个进程同时最多算 4 个；旧哈希在登录时自动换成新参数。
3. **提交作业慢**：原来逐题查询、写库，改成一次查出全部作答。提交的 p50 从约 450 ms 降到 70–90 ms。
